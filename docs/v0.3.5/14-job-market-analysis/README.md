## 先说清楚本章的数字纪律

旧版第 14 章有大量百分比和薪资数字：市场规模表、JD 关键词"出现频率"表、按城市和级别的薪资矩阵、"同比增长 300%+""内推通过率是海投的 3-5 倍"。这些数字**一个都没有出处**——没有平台名、没有报告名、没有采样时间、没有样本量、没有统计口径。

所以本章只做三件事：

| 处理方式 | 用在哪 | 长什么样 |
|---|---|---|
| **只讲方法论** | 岗位类型、技能栈、求职路径、面试流程 | 不给数字，给"你怎么自己判断"的步骤 |
| **给可核验的一手来源** | nanobot 自身的技术事实 | 带 `nanobot/...:行号`，你能当场翻源码 |
| **明确标注** | 任何我无法给出出处的市场判断 | `未验证（需自查）` + 去哪儿查、搜什么词、看什么指标 |

一句话：**本章的可信度来自"可复现"，不来自"看起来很精确"。** 你自己花两小时统计出的"30 份 JD 里 22 份写了 MCP"，比一份来路不明的"45%"有用一百倍——因为面试官追问"你怎么统计的"时，你答得出来。

## 一、2026年 AI Agent 市场概览

### 1.1 结论先行

**能确定的三件事**（都能自己核验）：

1. **框架已进入"工程化"阶段**。依据不是新闻而是代码：nanobot v0.3.5 是 329 个 Python 文件 / 约 99,398 行 SLOC、17 个渠道子包、46 条 Provider 记录——这是"要长期维护的产品"，不是周末玩具。
2. **需求集中在"能落地"的人身上**，而不是"会聊概念"的人。JD 里反复出现的是工具调用稳定性、上下文成本、多渠道接入这类工程词。
3. **技术栈在收敛**：Python + 异步 + 工具调用 + MCP + 检索，这五件事在绝大多数 Agent 相关 JD 里都会出现（定性判断；词频请自己统计，见 §三）。

**不能确定、要你自己查的**：市场规模、岗位数量、增长率、薪资中位数。这些每年都变，写死在教材里必然过期且极难核实。本章不给，§四教你怎么查。

### 1.2 需求侧的六个方向（方法论，不是数据）

| 方向 | 典型团队在做什么 | 你怎么验证它在招人 |
|---|---|---|
| 大厂 AI 平台团队 | Agent 开发平台（低代码编排、插件市场、知识库） | 搜"Agent 平台/智能体平台"+ 公司名，看 JD 有无"平台""开放能力""插件" |
| 垂直行业 Agent | 金融/医疗/法律/教育的定制 Agent | 搜"行业 + 智能体""行业 + 大模型应用"，看是否要求行业知识 |
| AI 原生创业公司 | 0→1 做 Agent 产品 | 看融资新闻时间点 + 招聘页岗位数（岗位多通常是刚拿钱） |
| 传统企业 AI 转型 | 智能客服、知识管理、内部流程自动化 | 搜"AI 应用""数字化"+ 行业词，JD 常写"内部系统对接" |
| 开发者工具 | IDE 插件、代码助手、测试自动化 | 搜"代码助手""研发效能"，看是否要求编译原理/静态分析 |
| AI 基础设施 | 推理服务、向量库、MCP 生态 | 搜"MCP""推理优化""vLLM"，看是否要求 CUDA/分布式 |

**正确用法**：不是背下来，而是看到一份 JD 时能一秒判断它属于哪一类——不同方向对"什么算好作品"的标准完全不同（见 §十一）。

### 1.3 一个可以自己核验的"行业温度计"

| 指标 | 怎么测 | 记什么 | 为什么可信 |
|---|---|---|---|
| 岗位数量周变化 | 同平台、同关键词、同城市，每周同一天搜一次 | 结果总数 + 截图 | 自己采的样，口径固定，趋势可比 |
| JD 技术栈词频 | 攒 30 份 JD 全文，数关键词 | 每个词出现在几份 JD 里 | 样本和口径都写在自己的表里 |
| 框架迭代速度 | 看目标框架的 release/tag 节奏 | tag 名 + 日期 | 一手信息，可核验 |

第三个指标可以立刻做一次：nanobot 的版本号写在 `pyproject.toml:3`（`version = "0.3.5"`），首发 2026-02-02，v0.3.5 是 2026-09-16。七个月从 0.1.x 走到 0.3.5——说明框架还在快速长，也意味着**你读到的任何教程都可能过期**。所以本章坚持给行号：行号会漂，但类名和函数名是稳定锚点。

## 二、常见岗位类型详解

五类岗位保留，但每类换成"职责 / 技术栈 / JD 怎么辨认 / 用 nanobot 哪里练 / 自查"。**薪资区间一律删除**，理由见 §四。

| 岗位 | 核心职责 | 技术栈 | JD 里怎么辨认 |
|---|---|---|---|
| AI 应用开发 | 调 LLM API 做功能、写 Prompt、搭后端 API | Python/TypeScript、一种 LLM SDK、FastAPI/Next.js、数据库 | 有"AI 功能""接入大模型""Prompt 调优"，但**没有**"Agent 循环""上下文治理" |
| LLM 应用 | 上下文策略、成本控制、模型选型与评测 | Python 异步、Prompt 工程、RAG、评测、可观测性 | 有"上下文管理""Token 成本""模型评测""A/B" |
| AI Agent 开发 | Agent 循环与停止条件、工具与 MCP、记忆与状态、评测体系 | asyncio、工具调用协议、MCP、向量库、系统设计 | 有"Agent 架构""工具调用""多 Agent""记忆"，且要求"读过源码" |
| 大模型算法 | SFT/DPO/LoRA、数据清洗、评测、推理加速 | PyTorch、分布式训练、Transformer 细节 | 有"训练""微调""论文""顶会"，通常要求硕博 |
| AI 产品经理 | 需求拆解、交互设计、能力边界沟通、数据分析 | 技术只要求"了解" | 有"需求分析""用户增长""竞品" |

**用 nanobot 练什么（对应上表五类）**：

1. **应用开发**：跑通 [06 章](../06-install-and-hands-on/README.md)，用 `nanobot serve` 起 OpenAI 兼容接口，写个最小前端去调——覆盖这类岗位 80% 的日常。
2. **LLM 应用**：system prompt 的拼装顺序在 `nanobot/agent/context.py:101`；上下文治理配置对象是 `ContextGovernanceConfig`（`nanobot/agent/context_governance.py:113`），工具结果上限只是它的一个字段（`:119`，对应配置项 `max_tool_result_chars`，默认 16,000，`nanobot/config/schema.py:131`）。读懂这三处，你就能回答"上下文满了怎么办"。
3. **Agent 开发**：`AgentLoop`（`nanobot/agent/loop.py:196`，管回合）与 `AgentRunner`（`nanobot/agent/runner.py:308`，管循环）的分工；迭代上限 `max_tool_iterations=200`（`nanobot/config/schema.py:129`，循环体在 `nanobot/agent/runner.py:435`）；工具发现的 scope 过滤（`nanobot/agent/tools/loader.py:100`）。
4. **算法**：不用改 nanobot，但要理解模型侧边界。切入点：`nanobot/providers/registry.py:146` 起的 `PROVIDERS` 元组有 46 条 `ProviderSpec`，每条说明"怎么连、读哪个环境变量、支不支持缓存"——这是"统一消息格式翻译成各家 wire format"的工程答案。
5. **产品**：亲手跑 `nanobot onboard --wizard` 与 `nanobot gateway`，再读 [09 章](../09-multi-platform/README.md)—17 个渠道分别要什么字段、哪些必须 `enabled: true`，这些决定"功能能不能明天上线"。

**五句自查**（答不上就说明你只是"听过"）：① 不看文档写出"结构化输出 + 重试 + token 计数"？② 20 万窗口、成本降 30%，说得出三个杠杆和各自主作用？③ 画得出"一条消息从进来到回复"的链路并说出每段失败长什么样？④ 解释"temperature 调低为什么不能消除幻觉"？⑤ 说清"Agent 的失败不是报错，而是很自信地做错事"？

## 三、JD 关键词深度分析

旧章那张"出现频率"表（Python 95%、异步 65%…）没有采样口径、不可复现，本章不再沿用。下面给"关键词 → 为什么 JD 会写它 → 你拿什么证明"，频率自己算（方法见 3.2）。

### 3.1 六组关键词

| 组 | 关键词 | 为什么 JD 会写 | 你要拿出的证据 |
|---|---|---|---|
| 语言工程 | Python + 类型注解 | 代码库几乎全 Python | 一个 mypy/pyright 通过的项目 |
| | asyncio | 一个回合要并发跑多个工具 | 讲清 `Lock`/`Semaphore`/`gather` 的区别 |
| | REST/gRPC、Docker、Git/CI | 服务间调用、交付、协作底线 | 真实 API 集成（含重试超时）、能一键起的仓库、有意义的 commit |
| Agent 编排 | Agent 循环 / ReAct | 岗位核心 | 画得出停止条件与失败分支 |
| | Tool / Function Calling | 一切能力的入口 | 自己写过一个工具并被模型成功调用 |
| | 多 Agent / 子 Agent | 复杂任务拆解 | 讲清"为什么拆"和拆分后的失败模式 |
| | 工作流编排 | 生产要确定性 | 区分"workflow 决定何时跑"与"agent 决定怎么跑" |
| | 框架源码（任一） | 区分"会调 API"与"懂机制" | 一个能当场翻到的类名 + 行号 |
| 协议工具 | MCP | 工具生态的接口标准 | 自写一个 MCP Server 并接进宿主 |
| | JSON Schema / OpenAPI | 工具参数契约、HTTP→工具 | 手写 `parameters` 并能解释每个字段；用 OpenAPI 生成过工具 |
| | Webhook / 长连接 | 平台接入的两种形态 | 讲清为什么有的平台不需要公网回调 |
| 检索知识 | RAG | 知识更新与引用 | 端到端链路 + 一组可复现的评测数字 |
| | 向量库 / Embedding | 召回 | 一次"换 embedding 模型后召回变化"的记录 |
| | 混合检索 / Rerank | 专有名词召回差 | 对比表（只用向量 vs 加 BM25） |
| | 引用与权限 | 企业落地硬要求 | 按 ACL 过滤 + 答案带文档 ID |
| 模型推理 | Prompt 工程 | 所有 AI 岗的基本功 | 带版本管理、能 diff 的 prompt 目录 |
| | 上下文管理 / 成本优化 | 长会话命门、直接等于毛利 | 压缩前后 token 与效果对比；"改了什么/省了多少/代价是什么"表 |
| | 模型评测 | 上线前必须回答 | 评测集 + 指标定义 + 复现命令 |
| 数据对齐 | SFT/RLHF/DPO/LoRA、PyTorch、Transformer | **只在算法岗是硬要求** | 真跑过的实验记录 |

> 应用岗把"DPO/LoRA"写上去不加分，反而会招来"β 取多少、为什么"的追问。

### 3.2 一个词 = 一个证据，以及自己算词频的五步

判断标准：**把简历上这个词划掉，你的项目还成立吗？** 成立就是装饰，不成立才是能力。面试官问"你写的 MCP 是哪种传输"，你要能答"stdio 跑通的是本地那个，HTTP 那个用 streamableHttp"。

自己统计：① **取样**：2 个平台、一批关键词、同一城市、前 3 页，攒够 30 份 JD 全文（编号 01–30）；② **定口径**：一份 JD 内出现多次只算 1 次、同公司同岗位只留 1 份、只统计"要求/加分"段；③ **数**：Excel 或 `for kw in kws: sum(kw in jd for jd in jds)`；④ **分组**：必备（>2/3）/常见（1/3–2/3）/少见（<1/3），别用百分比炫耀精度；⑤ **记偏差**：写一句"样本来自搜索结果前 3 页"——**主动交代偏差是加分项**。

## 四、薪资范围参考

### 4.1 为什么这一节没有数字

1. 薪资随城市、级别、公司阶段、年份剧烈变化，写死必然过期。
2. **口径不可比**：同样的"30K"可能是 base、可能是含绩效的月均、可能是"月薪 ×16 ÷12"。旧章表格完全没交代口径。
3. 编造薪资对读者伤害最大：拿假数字去谈薪，要么被压价，要么谈崩。

### 4.2 三类可核验的信息源

| 来源 | 具体去哪 | 能看到什么 | 局限 |
|---|---|---|---|
| 招聘平台挂牌区间 | 各招聘 App 岗位详情页 | 公司自己写的区间 | 区间极宽，常是"引流价"，不含股票 |
| 社区自报 | 脉脉、看准、Blind、Levels.fyi 一类 | 真实 offer 数字 | 自报有炫耀偏差、样本小 |
| 官方/机构报告 | 招聘平台年度人才报告、薪酬调研报告 | 分位值、同比 | 发布有周期，常滞后一年；要看样本与方法 |

**用法**：三类交叉。平台告诉你"想给多少"，社区告诉你"实际给了多少"，报告告诉你"大盘在哪"。差距大时以**社区自报 + 你的面试实感**为准。引用时必须写清**报告名 + 发布方 + 发布时间**；写不出就标 `未验证（需自查）`。

### 4.3 谈薪前必须问清的六个口径

① base 是多少（固定几个月？含浮动吗）② 年终奖发放条件（写进合同还是"视业绩"）③ 股票/期权的数量、行权价、归属节奏、估值依据 ④ 签字费/搬家费是否一次性 ⑤ 社保公积金基数（全额还是最低）⑥ 试用期折扣（有没有 80%）。

六条问清，才能把两个 offer 放同一张表比较。旧章"大厂总包通常为月薪 ×（14-18）"没有来源且各厂差异极大——别拿它做决策。

### 4.4 薪资调研表（自己填）

| 公司 | 岗位 | 级别 | 挂牌区间 | 社区自报 | 面试确认的 base | 总包构成 | 来源 + 记录日期 |
|---|---|---|---|---|---|---|---|
| 例：A 公司 | LLM 应用 | 中级 | 25–40K | 32K×15 | 未确认 | 未确认 | 平台详情页 + 社区帖，2026-10-01 |

填不满是正常的。**空着比编一个数字好。**

## 五、主要招聘平台与渠道

### 5.1 平台清单（按用法分类，不按"岗位数量"排）

| 类型 | 代表 | 适合阶段 | 注意 |
|---|---|---|---|
| 即时沟通型 | BOSS 直聘一类 | 社招主力，可直接和用人方聊 | 回复率取决于打招呼质量，不是数量 |
| 校招/社区型 | 牛客一类 | 应届、实习、笔试信息 | 面经多，要甄别年份 |
| 中高端猎头型 | 猎聘一类 | 3 年以上、管理岗 | 猎头会改你的简历，务必自己终审 |
| 人脉内推型 | 脉脉、即刻、微信群、Discord | 所有阶段，效率最高 | 先给价值（答题/贡献代码）再求内推 |
| 海外/外企 | LinkedIn 一类 | 远程、外企 | JD 常是英文，注意时区与签证 |

> ⚠️ 旧章列的 **GitHub Jobs 已于 2021 年 8 月关停**，别再照着旧清单搜。平台会死，**方法不会**：找"技术人员聚集 + 有招聘板块"的地方，而不是记平台名。

### 5.2 三个被低估的渠道 + 每天 30 分钟日程

被低估的三个：**开源项目的 issue/discussion**（维护者常在里面招人，一个真实 PR 胜过十份简历）、**技术博客的评论区**（写一篇"我读了 nanobot 的 XX 模块"会有人来找你）、**前同事/前同学**（冷启动最快、几乎零成本）。

| 时段 | 动作 | 产出 |
|---|---|---|
| 10 分钟 | 刷 2 个平台新增岗位，收藏匹配的 | 收藏夹 +5 |
| 10 分钟 | 给 3 个岗位写**定制**打招呼（不群发） | 3 条针对性消息 |
| 10 分钟 | 维护 1 个开源/博客产出 | 1 次 commit 或 1 段笔记 |

**不要做**：一天海投 50 家。海投的唯一效果是被同一套 HR 系统标记为"不匹配"。

## 六、大厂 AI Agent 团队介绍

### 6.1 为什么这一节改成"怎么核实"

## 七、必备技能清单

八个技能保留，每条改成"为什么 JD 要 / 自检 / 在 nanobot 哪里练"。

| 技能 | 为什么 JD 要 | 自检问题 | 在 nanobot 哪里练 |
|---|---|---|---|
| Python + 异步 | 每个回合都在并发跑多个 IO | `Lock` 与 `Semaphore` 各保证什么？`gather` 里一个协程抛异常，其他会怎样？ | `nanobot/agent/loop.py:403` 的 `_session_locks`；`:429` 起的全局并发闸门（容量来自环境变量 `NANOBOT_MAX_CONCURRENT_REQUESTS`，**不设即不限**） |
| LLM API + Prompt | 所有 AI 岗的日常操作 | 结构化输出失败怎么兜底？token 怎么算？流式怎么处理中断？ | `nanobot/agent/context.py:101`，注意"稳定内容在前"是为了命中缓存 |
| Agent 架构 | "会调 API"与"会做 Agent"的分水岭 | 循环何时停？工具报错会中断回合吗？子 Agent 为什么拿不到 `spawn`？ | `nanobot/agent/runner.py:435`、`nanobot/agent/tools/spawn.py:63`、`nanobot/agent/tools/loader.py:100` |
| MCP 协议 | 工具生态在向它收敛 | 三大原语？stdio 与 HTTP 怎么选？工具名怎么命名？ | [05 章](../05-mcp-protocol/README.md)；配置在 `tools.mcpServers`，工具名 `mcp_<server>_<tool>` |
| RAG 系统 | 知识类需求最成熟的解法 | 切块怎么定？专有名词为何召回差？为何还要 rerank？ | 把"检索"包成工具（统一执行入口 `nanobot/agent/tools/registry.py:187`）或做成 MCP server |
| 大模型原理 | 定位"模型不行"还是"工程不行" | KV Cache 为何让长上下文变贵？温度调低为何不能消除幻觉？ | `nanobot/providers/registry.py:146` 起的 46 条 `ProviderSpec` |
| 系统设计 | 中高级岗必考 | 多租户怎么隔离？失败怎么观测？成本怎么归因？ | [11 章](../11-security-and-deploy/README.md)；注意 `tools.restrict_to_workspace` 默认 **false**（`nanobot/config/schema.py:401`），即"默认配置不适合多用户部署" |
| 工程素养 | 决定能否把 demo 变成产品 | 别人能一键跑起来吗？有测试吗？密钥会进 git 吗？ | 看它的测试规模（约 31,631 行）与 `${VAR}` 只在内存展开、不回写文件的配置校验 |

**每个技能都要有产出物**：一张时序图、一个带版本管理的 prompt 目录、一个能跑通的仓库、一次换模型的实测记录。没有产出物的"技能"在面试里等于零。

**中优先级（按方向选，选了的要能答 3 层追问）**

### 8.2 每个关键词都必须能指向一个物件

| 关键词 | 没有证据的写法 | 有证据的写法 |
|---|---|---|
| MCP | "熟悉 MCP 协议" | "实现 1 个 MCP Server（3 个工具，stdio + streamableHttp 双传输），接入 nanobot 后完成 X 任务" |

## 九、面试流程介绍

### 9.1 典型流程（四段式）

```
简历筛选 → 一面（基础技术）→ 二面（技术深度/项目）→ 三面（Leader/交叉）
→ HR 面 → Offer 沟通
```

**注意**：具体轮次、时长、是否有笔试**每家公司都不一样**，以 HR 通知为准。旧章"通常 2-4 周"没有来源，别拿它规划档期——按"投递后随时可能约面"准备更稳。

### 9.2 各轮考察什么、怎么准备

| 轮次 | 考察什么 | 怎么准备 | 常见坑 |
|---|---|---|---|
| 一面（45–60 分钟） | Python、数据结构、LLM 基础、Agent 基本循环、1 个项目简述 | LeetCode 中等 30–50 题（字符串/哈希/树/DP）；把 [13 章](../13-interview-bagua/README.md) Q1–Q10 讲成 90 秒版 | 把"ReAct"背成"思考和行动"，却说不出你代码里哪一行体现了它 |
| 二面（60–90 分钟） | 项目深挖、架构取舍、系统设计、开放题（怎么评测/控成本） | 用 STAR 讲一个项目；准备 3 个系统设计草图 | 简历写了"源码研究"却报不出一个类名 |
| 三面（45–60 分钟） | 技术判断力、协作、规划、行业理解 | 准备 2 个"技术决策"故事（选型、取舍、后悔的决定） | 大谈"增长 300%"，被问来源答不上来 |
| HR 面 | 动机、稳定性、薪资期望、文化匹配 | 按 §4.3 六口径算清，给区间不给点 | 对薪资构成一无所知 |

### 9.3 用 nanobot 讲深：三个安全话题

| 话题 | 一句话钩子 | 深挖时的退路 |
|---|---|---|
| 回合与循环的分工 | "Loop 管回合，Runner 管循环" | `nanobot/agent/loop.py:196` / `nanobot/agent/runner.py:308` |
| 迭代上限 | "只有一个 `max_tool_iterations`，默认 200，子 Agent 继承" | `nanobot/config/schema.py:129`、`nanobot/agent/runner.py:435` |
| 并发控制 | "会话锁 + 可选全局信号量 + 子 Agent 信号量" | `nanobot/agent/loop.py:403`、`:429` |

原则：**先说结论，再说证据，最后主动交代边界**（"这是 v0.3.5 的行为，更早版本我没考证"）。

## 十、求职时间线规划

### 10.1 相对时间线（不绑具体月份）

旧章把时间线钉在 2026 年 1–10 月，写死就过期。改成"第 N 周"，从任何一天开始都能用。

| 阶段 | 重点 | 产出（可验收） |
|---|---|---|
| 第 1–2 周 | 打基础：读完 01–05 章，跑通 nanobot | 能 `nanobot -m "hi"` 跑通并解释链路 |
| 第 3–4 周 | 动手：06–10 章，写第一个工具 | 一个能被模型成功调用的自定义工具 |
| 第 5–6 周 | 作品集：完成 §十一 至少一个方向 | 一个仓库 + README + 演示 |
| 第 7–8 周 | 表达：13 章 70 题 + 简历定稿 | 90 秒能讲完 20 题 |
| 第 9–12 周 | 投递与面试：每周 3–5 场 | 面试记录表（问了什么、砸在哪） |
| 第 13 周起 | 复盘与谈判 | 2 个以上 offer 的对比表 |

### 10.2 应届 vs 社招

- **应届**：可拉长到 3 个月，但要在"实习/项目"上先占位；笔试别等投递才开始刷。
- **社招**：压到 6–8 周，重点是"把已有经验翻译成 Agent 语言"——高并发、稳定性、成本优化都是硬通货。

### 10.3 每日投入（建议，不是标准）

早上 30 分钟刷 1–2 道八股；上午 2–3 小时读源码或写项目；下午 1–2 小时算法题；晚上 1–2 小时理论（RAG/MCP/系统设计）；睡前 30 分钟行业动态 + 一条笔记。

**唯一硬标准**：每天有一个**可指认的产出**（一行 commit、一段笔记、一道题的解法）。没有产出的"学习 8 小时"等于零。

## 十一、用 nanobot 做求职作品集的 3 个方向与验收标准

作品集的目的不是"多一个项目"，而是**给面试官一个可以追问 30 分钟而不塌的东西**。

**共同验收维度（缺一不算完成）**：可运行（别人 clone 后 10 分钟跑通）/ 可复现（关键数字有命令能重跑）/ 可解释（能画出数据流并报出类名）/ 有边界（说得出何时会失败）/ 有取舍（说得出"为什么不用另一种方案"）。不合格信号：**"我这台机器上可以"**、**"数字在我脑子里"**、**"调了个库"**、**"没有失败场景"**、**"教程这么写的"**。

### 方向 1：给 nanobot 加一个真实可用的工具（Agent 开发方向）

在 `nanobot/agent/tools/` 下新建一个 `Tool` 子类，解决你自己真实遇到的问题（查内网 API、批量重命名、读某格式日志）。

| 验收项 | 标准 | 怎么证明 |
|---|---|---|
| 被发现 | 不改注册表，重启即被 `ToolLoader` 自动发现 | 录屏：`nanobot` 里问"你有哪些工具" |
| 契约完整 | 实现 `name`/`description`/`parameters`/`execute`，`parameters` 是合法 JSON Schema | 代码 + 一次成功调用 |
| 作用域 | 明确该不该给子 Agent 用（`_scopes`），并说明理由 | `nanobot/agent/tools/loader.py:100` |
| 错误处理 | `execute` 不抛裸异常，用 `ToolResult.error(...)` 返回可读错误 | 故意传错参数，展示模型正确消化 |
| 可测可讲 | 3 个单测（正常/参数错/外部失败）；README 写清"为什么这个工具值得存在" | CI 绿 + 200 字设计动机 |

**加分**：把工具做成 `read_only=True`，观察它是否被并发批处理（`nanobot/agent/tools/execution.py`）——这个观察本身就是面试素材。

### 方向 2：写一个 MCP Server 并接进 nanobot（平台/协议方向）

实现 3 个工具（读 + 查 + 写各一个），在 `config.json` 的 `tools.mcpServers` 注册，让 nanobot 完成任务。

| 验收项 | 标准 | 怎么证明 |
|---|---|---|
| 传输 | stdio 与 HTTP（streamableHttp 或 sse）**至少跑通一种**，说清另一种差别 | 配置片段 + 连接日志 |
| 命名 | 模型侧工具名符合 `mcp_<server>_<tool>` | 一次工具调用记录 |
| 描述质量 | 每个 `description` 能让模型在 5 次内选对 | 一组"该选 A 却选了 B"的案例与改进 |
| 健壮性 | 外部依赖挂了不影响宿主其他工具 | 拔掉依赖演示 |
| 安全 | 写操作有确认或白名单；凭据不写在 `env` 明文 | 代码 + 配置说明 |

**加分**：同一份 Server 接进第二个支持 MCP 的宿主，证明"一次开发，多处复用"不是口号。

### 方向 3：真实渠道 + 定时任务做成闭环（平台/后端方向）

用 `nanobot gateway` 接一个真实渠道（飞书/Telegram/Slack 任选），配一个 cron 任务（如每天早上汇总一个信息源），跑满 7 天。

| 验收项 | 标准 | 怎么证明 |
|---|---|---|
| 渠道可用 | 配置显式 `"enabled": true`，能收发真实消息 | 聊天截图（打码） |
| 权限收敛 | 配 `allowFrom` 白名单，陌生人被拒 | 另一个账号测试 |
| 任务可靠 | cron job 持久化，重启后不重复不丢失 | 重启演示 + 日志 |
| 可观测 | 每天记录"跑了没、花了多少 token、失败在哪" | 7 天表格 |
| 有结论 | 说得出"这 7 天最脆的一环是什么" | 一段复盘 |

**加分**：把 7 天真实数据（成功/失败次数、单次平均 token）写进简历——这是**唯一可以放心写进简历的数字**，因为你自己采样、自己能复现。

**组合建议**：只有 4 周做方向 1；有 8 周做方向 1 + 3；投平台/基础设施做方向 2 + 3。**不要三个都做**——两个做深 > 三个做浅，面试官只会深挖最靠前的那一个。

## 本章总结

1. **数据纪律**：没出处的数字不写。要么给可核验来源，要么标 `未验证（需自查）` 并给自查方法。
2. **方法论比结论长寿**：岗位分类、技能栈、读 JD 的方法、面试四段式五年后还能用；"2026 年增长 300%"明年就是垃圾。
3. **nanobot 的技术事实可当场核验**：99,398 行 / 329 文件 / 17 渠道 / 46 条 Provider 记录，从 `pyproject.toml:3` 到 `nanobot/agent/loop.py:196` 都能翻。
4. **作品集要有边界**：说得出"它什么时候会失败"的人，比声称"什么都能做"的人可信。
5. **谈薪先谈口径**：base、年终、股票、签字费分开算，问清六个口径再比。

## 附录 B：进阶理解（为什么招聘市场数据这么难核验）

**1. 招聘数据是"挂牌价"，不是"成交价"。** 平台写 25–40K，可能 25K 起、也可能"给到 40K 但要求 5 年"。把挂牌区间取平均，既不是中位数也不是众数，而是一个没有统计意义的数——旧章薪资表最根本的问题是**它不是错的，它是无意义的**。

**2. 样本天然有偏，且偏差方向固定。** 搜"AI Agent"出来的岗位标题普遍堆满关键词，真正做 Agent 的岗位可能叫"后端开发（LLM 方向）"。所以任何基于关键词搜索的词频统计都会**高估热词普遍性**。解决办法不是消除偏差，而是**声明偏差**。

**3. "增长率"需要基期，而基期常被藏起来。** "同比增长 300%"里的"去年"是哪一年？口径是岗位数还是 HC？统计全行业还是某平台？缺任一项都无法比较。看到增长率先问基期，是数据素养第一课。

**4. star 数不是技术指标。** 旧模板拿"37K stars"当论据（见第 15 章勘误）。star 受新闻、发布时间、社区运营影响，和代码质量没有稳定关系，而且会变。**能当论据的是代码规模、模块划分、测试规模、发布节奏**——nanobot v0.3.5 对应数字是 329 文件 / 约 99,398 SLOC / 约 31,631 行测试。

**5. 为什么"读过源码"仍然稀缺。** 它成本高、收益慢、且无法伪造——面试官问"子 Agent 为什么拿不到 `spawn`"，读过的人答"子 Agent 的注册表按 scope 过滤，`spawn` 没声明 `subagent` 作用域"（`nanobot/agent/tools/loader.py:100`），没读过的人只能猜"大概是权限限制"。**能被当场验证的知识，溢价最高。**

**6. 为什么本章坚持给行号。** 行号会漂，看起来"不稳定"。但它的价值是**可反驳**：你按行号翻过去，对不上就是文档错了。一份"不可反驳"的文档（只有结论没有证据）价值为零——这也是旧章最大的问题。

## 附录 C：如何结构化读 JD

一份 JD 通常 300–800 字，信息密度很低。**结构化读**=把它拆成五个固定栏位，用自己的话填一遍，你就知道该不该投、该补什么。

### C.1 五栏拆解法

| 栏位 | 从 JD 哪句来 | 你填什么 | 用途 |
|---|---|---|---|
| ① 硬门槛 | 学历、年限、语言、地点 | 满足 / 不满足（不可变且不满足 → 直接放弃） | 止损 |
| ② 技术栈 | "熟悉/掌握/精通 XXX" | 逐项标：能讲原理 / 用过 / 只听过 | 决定简历怎么排 |
| ③ 职责动词 | "负责/参与/设计/搭建/优化" | 提取动词，看主动还是被动 | 判断岗位真实层级 |
| ④ 成果指标 | "提升/降低/支撑 XXX" | 记下它关心的指标（延迟？成本？成功率？） | 决定面试讲哪个项目 |
| ⑤ 团队上下文 | "从 0 到 1""平台化""支撑 N 个业务" | 判断建设期还是维护期 | 决定讲"造"还是讲"稳" |

### C.2 动词是 JD 里信息量最大的词

| JD 用词 | 真实含义 | 你该怎么准备 |
|---|---|---|
| 负责搭建 / 从 0 到 1 | 没有现成系统，要你造 | 讲架构取舍、讲最小可用版本 |
| 负责优化 / 提升 | 系统已在，但有问题 | 讲定位过程、讲度量方法 |
| 参与 / 配合 | 你是执行位，上面有人 | 讲执行细节与协作 |
| 支撑 N 个业务方 | 你是平台方，要对 SLA 负责 | 讲稳定性、讲接入成本 |
| 探索 / 预研 | 结果不确定，可能不出活 | 讲学习速度、讲技术判断 |

**陷阱**：一份 JD 同时写"从 0 到 1"和"支撑 10 个业务方"，通常说明它把"平台建设"和"平台运营"混着写了——面试时问一句"这个岗位更偏建设还是运营"，比猜有用。

### C.3 一个标注示例

> 【职责】负责智能助手 Agent 的能力建设【③建设期】，设计并优化工具调用链路【③设计+优化，④关心成功率】；参与 RAG 知识库方案选型【③参与，说明上面有人定方向】。
> 【要求】3 年以上 Python【①硬门槛】；熟悉 asyncio 与常见 Agent 框架，有 MCP 实践者优先【②必备 + 加分】；有大规模在线服务经验者优先【②加分，④关心稳定性】。

读完的动作：简历第一屏放"工具调用链路"相关项目；准备一个"成功率怎么度量、怎么提升"的故事；MCP 只是"听过"就别写进简历。

### C.4 三个陷阱

① **把"加分项"当"必备项"**：要么不敢投，要么把不熟的写上去被追问露馅。② **只看技术栈不看动词**：同样叫"Agent 开发"，建设期和维护期要的人完全不同。③ **忽略团队上下文**：3 人团队和 300 人平台的同名岗位，日常差别巨大。
